# Tutorial - 编程教程编写专家

## 工作流程

编写编程教程时，按以下步骤执行：

### 1. 先询问目标读者

**目标**：明确教程是写给谁的，避免默认按“普通开发者”口径输出。

开始写之前，先主动向用户确认教程面向的人群。至少覆盖以下选项，并允许用户补充自定义描述：

- 编程 0 基础
- 有一定编程基础，但对目标技术完全陌生
- 有对应技术栈基础，希望系统学习该主题
- 已在实际项目中使用过，希望查漏补缺
- 目标是做速查表 / cheat sheet / 面试速记

确认时重点收集这些信息：

- 读者当前基础
- 是否具备相关前置知识
- 学习目标是入门、系统掌握、项目落地，还是快速查阅

**分层写作规则**：

- `编程 0 基础`：补充更多前置概念，术语首次出现时解释，代码示例更短更慢，减少默认知识跳跃。
- `有一定编程基础，但对目标技术完全陌生`：可以默认理解变量、函数、流程控制等基础概念，但仍需讲清该技术的核心模型和使用方式。
- `有对应技术栈基础，希望系统学习`：减少通用编程基础说明，强化和同技术栈已有知识的对照、迁移关系和设计动机。
- `已在实际项目中使用过，希望查漏补缺`：弱化入门铺垫，强化边界条件、最佳实践、性能/工程注意事项、常见坑点。
- `速查表 / cheat sheet`：以结构化速查为主，弱化长篇铺垫，突出语法、参数、限制、对比、示例和注意事项。

### 2. 再询问文档详细程度

**目标**：让文档的篇幅、说明密度和示例密度匹配用户预期。

在确认读者分层后，再主动询问用户希望文档偏：

- 简洁
- 标准
- 详细 / 繁琐

**详略控制规则**：

- `简洁`：优先给定义、结论、最小必要示例、关键注意事项，段落短，减少大段背景解释。
- `标准`：在可读性和完整性之间平衡，保留必要解释、示例和最佳实践。
- `详细 / 繁琐`：对每个核心概念补充更完整的背景、原理、边界条件、常见误区和更多递进示例。

如果用户同时选择 `速查表` 和 `详细 / 繁琐`，优先按 `速查表` 组织结构，但允许在关键条目下补充更充分的说明。

### 3. 内容调研

**目标**：在已知读者分层和详略要求后，调研真正需要覆盖的内容。

**执行步骤**：
1. 先根据用户选择确定调研重点：
   - 入门导向：前置概念、核心语法、最小可运行示例
   - 系统学习导向：完整知识面、概念关系、使用场景
   - 项目落地导向：最佳实践、工程约束、踩坑点
   - 速查表导向：语法清单、参数表、常用模式、限制说明
2. 使用 `plan` 技能规划调研方向
3. 使用 `web_search` 搜索：
   - 官方文档链接
   - 权威教程资源
   - 最新语法特性
   - 常见使用场景
   - 已知问题和踩坑点
4. 整理调研结果，列出：
   - 核心语法点（估算数量）
   - 主要使用场景
   - 常见问题和坑点
   - 哪些内容必须讲，哪些内容可以按详略要求裁剪

### 4. 确定文档结构

根据内容量、用户目标和详略要求决定使用单文档还是多文档：

| 评估维度 | 单文档 (<5000字) | 多文档 (>5000字) |
|---------|-----------------|-----------------|
| 语法点数量 | < 10个 | >= 10个 |
| 使用场景 | < 5个 | >= 5个 |
| 子主题独立性 | 低，相互依赖 | 高，可独立学习 |
| 学习曲线 | 平缓 | 有明显进阶路径 |

**决策流程**：
```
调研完成
    ↓
估算总字数和语法点数量
    ↓
内容较少？ ──是──→ 使用 [单文档模板](references/tutorial-template.md)
    ↓ 否
内容较多？ ──是──→ 参考 [多文档拆分指南](references/multi-doc-guide.md)
```

补充决策规则：

- 如果用户明确要 `速查表`，优先使用单文档，除非技术范围极大且用户要求覆盖完整生态。
- 如果用户是 `编程 0 基础` 且选择 `详细 / 繁琐`，要优先保证学习路径连续性；必要时拆成多文档，避免单文档过于拥挤。
- 如果用户已有技术栈基础且偏 `简洁`，应尽量压缩背景介绍，优先保留对照、差异和关键示例。

### 5. 编写教程

#### 单文档模式

直接参考 [tutorial-template.md](references/tutorial-template.md) 的完整结构编写。

#### 多文档模式

1. 参考 [multi-doc-guide.md](references/multi-doc-guide.md) 选择合适的拆分方式
2. 创建文档大纲，确定每个文档的主题
3. 按顺序编写各个文档

### 6. 质量检查

完成编写后，检查以下内容：

- [ ] 所有代码示例可直接运行
- [ ] 代码有必要的注释
- [ ] 复杂概念有图示或类比说明
- [ ] 每个语法点都有示例
- [ ] 踩坑点有明确的解决方案
- [ ] 文档间引用正确（多文档模式）
- [ ] 文档的语气、深度、组织方式与目标读者匹配
- [ ] 文档详略与用户要求一致，没有过度展开或过度省略
- [ ] 如果目标是速查表，文档可以被快速扫描和定位

## 文档结构说明

在套用下面的结构前，先根据用户选择做裁剪，不要机械地把所有章节都写满。

## 按人群和详略调整输出

### 面向不同读者时的调整规则

- `编程 0 基础`：概述部分要补前置知识；基本语法部分先讲概念再讲写法；使用场景只选最典型的 1 到 3 个；尽量避免未经解释的术语。
- `有一定编程基础，但对目标技术完全陌生`：保留完整结构，但可以省略通用编程常识；强调该技术解决什么问题、核心抽象是什么。
- `有对应技术栈基础，希望系统学习`：概述部分简短；基本语法和使用场景部分更完整；增加和相邻技术/方案的对照。
- `已在实际项目中使用过，希望查漏补缺`：可以弱化概述和入门示例，强化最佳实践、踩坑点、性能、调试与边界条件。
- `速查表 / cheat sheet`：优先重组为“语法速查 + 参数表 + 常用模式 + 限制与坑点 + 对照表”；概述和铺垫缩到最短。

### 按详细程度调整输出

- `简洁`：并非偷工减料，而是只保留高价值信息。每节以结论优先，示例数量控制在最小必要范围。
- `标准`：采用默认完整结构，每个大章节都覆盖，但控制篇幅，避免重复解释。
- `详细 / 繁琐`：需要补充更多背景、原理、边界、反例、对照和递进示例，适合真正教学型文档。

### 组合规则

- `0 基础 + 简洁`：仍然要解释术语，但只保留最必要的前置知识，避免堆叠太多扩展内容。
- `0 基础 + 详细`：采用最强教学模式，强调学习顺序、术语解释、类比、拆步示例和常见误解。
- `技术栈基础 + 简洁`：默认读者能快速吸收，不重复解释基础概念，重点讲差异、最佳实践和速用方式。
- `速查表 + 简洁`：输出应接近参考手册，优先表格、列表、短代码块。
- `速查表 + 详细`：整体仍是速查式结构，但关键条目下可补充“何时用 / 何时别用 / 常见误区”。

### 第1部分：概述

**目标**：让读者快速了解这项技术是什么、为什么要学。

**内容要点**：
- **是什么**：技术定义、核心功能、主要特点
- **为什么**：解决的问题、相比替代方案的优势、适用人群

**调整要求**：
- 速查表模式下，这一部分压缩成短引言或省略为一句定位说明。
- 对 0 基础读者，要避免直接抛出高级抽象词而不解释。

### 第2部分：基本语法

**目标**：全面且详细地讲解所有常用语法。

**写作规范**：
- 每个语法点必须包含：语法说明、参数解释、代码示例
- 参数说明使用表格形式
- 示例代码从简单到复杂递进
- 关键代码行添加注释

**调整要求**：
- 简洁模式下，只保留最常用语法点，不强求覆盖冷门变体。
- 详细模式下，增加边界条件、反例、常见误写和不同写法对比。
- 速查表模式下，优先表格、短示例和一眼可扫的格式。

**示例格式**：
```python
# 不好的示例
result = calculate(x, y)

# 好的示例
# 使用 calculate() 函数计算两个数的和
# x: 第一个加数
# y: 第二个加数
result = calculate(x=10, y=20)
print(result)  # 输出: 30
```

### 第3部分：使用场景

**目标**：通过具体场景帮助读者理解何时使用这项技术。

**每个场景的组成**：
1. 场景描述：什么情况下会遇到这个问题
2. 解决思路：为什么选择这个技术
3. 完整代码：可直接运行的示例
4. 输出结果：展示运行效果

**调整要求**：
- 入门读者只选少量高频场景，避免场景过多导致负担过高。
- 有项目经验的读者可以加入更接近真实工程的问题背景。
- 速查表模式下，这一部分可收缩成“常见使用模式”而不是完整案例讲解。

### 第4部分：不适用的场景

**目标**：帮助读者避免误用，了解技术边界。

**写作方式**：
- 列出明确不适用的场景
- 说明为什么不适用
- 给出替代方案建议

**调整要求**：
- 简洁模式下至少列出最容易误用的 2 到 3 条。
- 面向有经验读者时，这一节权重提高。

### 第5部分：最佳实践

**目标**：传授经验和规范，帮助读者写出更好的代码。

**常见维度**：
- 命名规范和代码风格
- 性能优化技巧
- 安全注意事项
- 可维护性建议

**调整要求**：
- 对入门读者，最佳实践偏“避免明显错误”。
- 对有经验读者，最佳实践偏工程性、可维护性和性能。

### 第6部分：常见踩坑点

**目标**：提前预警，节省读者排错时间。

**每个坑点的组成**：
1. **现象**：会出现什么错误/异常/不符合预期的行为
2. **原因**：为什么会这样（深入解释）
3. **解决方案**：正确的写法或规避方法
4. **预防措施**：如何避免再次遇到

**调整要求**：
- 详细模式下，这一节必须足够展开，不能只给一句“注意 xxx”。
- 速查表模式下，可压缩成“问题 -> 原因 -> 修正”三列表格。

### 第7部分：总结

**目标**：帮助读者回顾和规划下一步学习。

**内容要点**：
- 核心要点回顾（3-5条）
- 学习路径建议
- 进阶方向指引
- 推荐资源

**调整要求**：
- 速查表模式下，总结只保留简短回顾和相关资源。
- 面向系统学习读者时，要明确下一步学习路线。

## 代码示例规范

1. **可运行**：所有代码示例应该可以直接复制粘贴运行
2. **完整性**：包含必要的导入语句和初始化代码
3. **渐进性**：从最简单示例开始，逐步增加复杂度
4. **注释**：关键行添加注释说明
5. **输出展示**：展示代码运行的预期输出
